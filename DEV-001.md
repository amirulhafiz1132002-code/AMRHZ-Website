# DEV-001 — Verified Development State Model

**Repository:** AMRHZ-Website  
**Status:** LOCKED  
**Purpose:** Establish one consistent, evidence-driven state model for AMRHZ systems, projects, features, and development work.

## Core Principle

> STATE MUST REFLECT EVIDENCE, NOT UI APPEARANCE.

## State Vocabulary

- **CONCEPT** — idea or architectural concept with no implementation requirement yet.
- **PROPOSED** — identified idea or capability proposed for future consideration.
- **PLANNED** — intentionally scheduled or defined for implementation but not started.
- **DEVELOPMENT** — implementation is actively being developed.
- **PARTIAL** — some implementation exists, but the complete capability is not verified.
- **VERIFIED** — implemented and tested with sufficient evidence.
- **LIVE** — verified and operating in its intended real environment.
- **BLOCKED** — cannot continue because of a known dependency, limitation, or external blocker.
- **DEPRECATED** — no longer intended for active use.
- **UNKNOWN** — insufficient evidence to determine the actual state.

## Evidence Rules

Implementation/runtime claims should be supported by appropriate evidence such as repository implementation, commits, test results, runtime responses, deployment evidence, configuration evidence, or reproducible user-visible behavior.

Documentation and UI labels alone do not prove runtime capability.

## Transition Model

Normal progression:

`CONCEPT → PROPOSED → PLANNED → DEVELOPMENT → PARTIAL → VERIFIED → LIVE`

Exception states may include:

- `DEVELOPMENT → BLOCKED`
- `PARTIAL → BLOCKED`
- `VERIFIED/LIVE → DEPRECATED`
- `ANY STATE → UNKNOWN` when evidence becomes insufficient.

## Static vs Runtime

Static/documentary descriptions must remain distinguishable from runtime/verified capabilities.

A static capability may describe future architecture, but must not be presented as operational.

## Minimum Verification

Before a capability can be marked `VERIFIED`, AMRHZ should be able to answer:

1. What was implemented?
2. Where is the implementation?
3. How was it tested?
4. What was the result?
5. What environment was tested?
6. What limitations remain?

## Failure-Safe Rule

> Evidence wins over the displayed state.

If evidence conflicts with a displayed state, the state should be corrected rather than preserved optimistically.

## Scope

Initial scope:

- AMRHZ Website
- AMRHZ AI System
- AP1
- AP1 Web Console
- Architecture Core
- Development Hub
- Future AMRHZ ecosystem capabilities

## Implementation Boundary

DEV-001 defines state language and evidence requirements. It does not implement runtime health monitoring, authentication, databases, agents, or orchestration.

## Acceptance Criteria

- [x] State vocabulary defined.
- [x] Evidence expectations defined.
- [x] Static/documentary state separated from runtime state.
- [x] Failure-safe rule defined.
- [x] Website integration implemented for the Development Hub state registry.
- [ ] Runtime health monitoring is intentionally outside this task.

## Guiding Principles

- REAL STATE > UI SIMULATION
- EVIDENCE > CLAIM
- HUMAN INTENTION > AI ASSUMPTION
