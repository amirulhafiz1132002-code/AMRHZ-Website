# DEV-003 — Evidence Coverage & Claim Audit

**Repository:** AMRHZ-Website  
**Status:** PASS — AUDIT COMPLETE  
**Purpose:** Extend the evidence protocol beyond the Development Hub and audit public website status claims against observable repository evidence.

## Core Principle

> EVERY STATUS CLAIM SHOULD HAVE AN IDENTIFIABLE EVIDENCE BASIS OR AN EXPLICIT LIMITATION.

DEV-001 defines state meaning. DEV-002 defines the evidence structure supporting state. DEV-003 audits whether the broader AMRHZ Website consistently applies that model to its public-facing claims.

## Problem

DEV-001 and DEV-002 currently provide an evidence-backed state registry for the Development Hub.

The wider website also contains system and project status labels such as ACTIVE, BUILDING, and DOCUMENTED. These claims may describe real repository artifacts, but they are not yet systematically mapped to DEV-002 evidence records.

Without an audit, the website can contain a mixture of evidence-backed states and standalone presentation claims.

## Scope

DEV-003 initially audits:

- Systems section
- Projects section
- Development Hub
- Changelog
- Terminal
- Roadmap / planned content
- Other public-facing status claims found during inspection

The audit must distinguish:

- repository evidence
- rendered/static website evidence
- external/runtime evidence
- documentary or planned claims
- insufficient evidence

## Audit Model

Each audited claim should be evaluated as:

`CLAIM → EVIDENCE → SUPPORT LEVEL → STATE / LIMITATION`

Where practical, the audit records:

1. **Claim** — the exact capability or status being communicated.
2. **Location** — repository file/section where the claim appears.
3. **Evidence** — observable implementation or supporting artifact.
4. **Support Level** — what the evidence actually establishes.
5. **State** — DEV-001 state where applicable.
6. **Limitation** — what the evidence does not establish.
7. **Action** — preserve, clarify, map to evidence, or mark UNKNOWN.

## Support Levels

DEV-003 does not create a competing state vocabulary. It uses evidence scope to explain what a claim is supported by.

Suggested support categories:

- **REPOSITORY** — implementation/artifact exists in the repository.
- **STATIC_RENDERED** — behavior is observable in the rendered static website.
- **EXTERNAL_RUNTIME** — supported by a separately verified runtime or external service.
- **DOCUMENTARY** — documented concept, architecture, roadmap, or intent only.
- **INSUFFICIENT** — available evidence does not support the claim at its current strength.

Multiple support categories may apply to one claim.

## Rules

- Do not assume a status is true merely because it is displayed.
- Prefer direct repository evidence over descriptive labels.
- Do not upgrade static evidence into runtime capability.
- Do not treat roadmap intent as implementation evidence.
- Do not treat a project being named in the website as proof that its external runtime is operational.
- Preserve useful claims when evidence supports them, but narrow wording when evidence only supports a weaker statement.
- If evidence is insufficient, use an explicit limitation or UNKNOWN rather than inventing support.
- Do not silently remove uncertainty.
- Existing verified evidence records remain authoritative for their covered capabilities.

## Non-Goals

DEV-003 does not implement:

- backend persistence
- authentication or authorization
- autonomous agents
- orchestration
- AI execution
- runtime health monitoring
- new external integrations
- automatic claim promotion
- automatic state changes without evidence

DEV-003 is an audit and evidence-coverage task.
