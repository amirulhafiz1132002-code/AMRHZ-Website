# DEV-004 — Terminal Evidence & Interaction Verification

Status: LOCKED

## Objective

Verify the actual implementation state of the AMRHZ.SYS browser terminal by comparing its HTML structure with the JavaScript interaction layer, documenting evidence, and establishing the boundary between a static terminal interface and a functional browser interaction.

## Core Rule

`REAL STATE > UI SIMULATION`

A terminal-looking interface must not be treated as functional merely because it renders like a terminal.

## Audit Model

`TERMINAL CLAIM → HTML IMPLEMENTATION → JAVASCRIPT WIRING → TEST → RESULT → STATE / LIMITATION`

## Scope

1. Inspect `index.html` terminal markup and identifiers.
2. Inspect `script.js` terminal selectors, event handlers, and intended commands.
3. Compare the two implementations for exact wiring compatibility.
4. Determine which terminal capabilities are actually supported by repository evidence.
5. Determine whether the current terminal should be classified as functional, partial, static, or unknown.
6. Document the mismatch, if any, without silently correcting it.
7. Define a correction only if evidence supports a separate implementation step.
8. Test the verification result.
9. Create a checkpoint when all acceptance criteria pass.

## Required Evidence

The verification record must identify:

- terminal UI implementation location
- terminal input/output/form elements
- JavaScript selectors and event wiring
- intended command behavior
- exact compatibility/mismatch findings
- test method
- test result
- environment
- limitations
- resulting state

## Acceptance Criteria

- [ ] `index.html` terminal structure inspected.
- [ ] `script.js` terminal logic inspected.
- [ ] Selector/event compatibility explicitly verified.
- [ ] Intended terminal behavior documented from repository evidence.
- [ ] Functional vs static/partial boundary established.
- [ ] Any mismatch recorded without hiding it.
- [ ] No unrelated backend, auth, agent, orchestration, or runtime infrastructure added.
- [ ] Verification test passes.
- [ ] Checkpoint created after PASS.

## Non-Goals

DEV-004 does not implement:

- backend persistence
- authentication or authorization
- autonomous agents
- AI execution
- orchestration
- external integrations
- runtime health monitoring
- unrelated website redesign
- automatic promotion of development states

## Execution Order

`INSPECT → IMPLEMENT → TEST → PASS → CHECKPOINT`

For this DEV task, implementation means producing the verification/audit artifact and wiring only what is necessary to expose verified evidence. A functional terminal correction, if required, must be treated as a separately scoped implementation task unless explicitly included by a later lock.

## Failure-Safe Rule

If HTML and JavaScript evidence conflict, the documented state must reflect the conflict. Do not infer functionality from visual appearance.

## Expected Outcome

A reproducible, evidence-backed answer to:

> “Is the current AMRHZ.SYS browser terminal actually wired and functional, or is it currently only partially implemented/static?”
