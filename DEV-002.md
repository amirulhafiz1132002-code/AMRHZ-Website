# DEV-002 — Evidence / Verification Layer

**Repository:** AMRHZ-Website  
**Status:** LOCKED  
**Purpose:** Define a formal evidence model that connects observable implementation evidence to development state without claiming capabilities that are not evidenced.

## Core Principle

> EVIDENCE MUST EXPLAIN WHY A STATE IS TRUE.

DEV-001 defines the state vocabulary. DEV-002 defines the evidence structure required to support state claims.

## Problem

The current state registry can display states such as VERIFIED, PROPOSED, and UNKNOWN, but the registry itself is documentary/UI state. It does not yet provide a structured record explaining the evidence behind each state.

DEV-002 establishes that missing layer.

## Evidence Model

A capability evidence record should be able to identify:

1. **Capability** — what is being evaluated.
2. **State** — the current DEV-001 state.
3. **Implementation** — where the relevant implementation exists.
4. **Test** — how the implementation was tested.
5. **Result** — what the test/evidence showed.
6. **Environment** — where the verification occurred.
7. **Limitations** — what the evidence does not prove.

Conceptual structure:

```
CAPABILITY
  ↓
EVIDENCE
  ├── implementation
  ├── test
  ├── result
  ├── environment
  └── limitations
        ↓
      STATE
```

## Evidence Rules

- Repository evidence is preferred over UI claims.
- Runtime evidence is preferred when runtime capability is being claimed.
- A documentation-only record cannot prove runtime capability.
- A UI label cannot independently prove implementation or runtime capability.
- Evidence must be specific enough to reproduce or inspect where practical.
- Missing evidence must not be silently converted into a positive state.
- If evidence conflicts with a displayed state, the state must be corrected.
- Evidence records must preserve limitations and boundaries.

## Static vs Runtime

DEV-002 does not collapse static documentation and runtime verification into one category.

Examples:

- A committed HTML section may prove implementation in the repository.
- A rendered page may prove observable website behavior.
- A successful API response may provide runtime evidence.
- A documented future architecture provides proposal evidence only.

## Initial Scope

DEV-002 applies first to the AMRHZ Website and its Development Hub.

It may later support:

- AMRHZ AI System
- AP1
- AP1 Web Console
- Architecture Core
- future AMRHZ ecosystem capabilities

## Non-Goals

DEV-002 does not implement:

- databases
- authentication
- autonomous agents
- orchestration
- persistent feedback
- runtime health monitoring
- AI execution

Those require separate evidence and development tasks.

## Development Rule

Implementation must follow:

```
INSPECT → IMPLEMENT → TEST → PASS → CHECKPOINT
```

No state should be promoted merely because DEV-002 is locked.

## Relationship to DEV-001

DEV-001 answers:

> What does a state mean?

DEV-002 answers:

> What evidence supports that state?

Together:

> STATE = INTERPRETATION OF EVIDENCE

## Guiding Principles

- REAL STATE > UI SIMULATION
- EVIDENCE > CLAIM
- HUMAN INTENTION > AI ASSUMPTION
